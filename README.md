# pi coding agent — in a box 📦

A hardened, containerized home for the [pi coding agent](https://github.com/badlogic/pi-mono). It runs entirely on your machine, keeps your API keys and GitHub token out of the agent's reach, and can't escalate privileges or scribble outside your project folder.

> **"Almost secure"** is the honest framing. This is defense-in-depth for a *local* tool that runs every command without asking — not a bulletproof multi-tenant sandbox. It raises the cost of a rogue or confused agent leaking your credentials from "trivial" to "genuinely hard." Read the [Security Architecture](#-security-architecture) so you know exactly what is and isn't protected.

---

## What you get

- 🔒 **Credentials the agent can't read** — LLM keys live in a separate proxy container; your GitHub token lives in a root-only file. The agent uses both but never sees either.
- 🧱 **A read-only container** — the whole filesystem is read-only except your workspace and a few scratch mounts. Temp dirs are `noexec`, so nothing downloaded can be run.
- 🚫 **No privilege escalation** — `su`, `mount`, `passwd`, and friends are physically deleted from the image; all setuid bits are stripped.
- 🔎 **Batteries-included pi** — LSP, linters, web search, sub-agents, and a curated extension set are baked in so pi feels like Claude Code out of the box.
- 🎮 **Optional GPU passthrough** — an overlay for NVIDIA GPUs when you want the agent to run local ML work.

## Quick Start

**1. Configure**

```bash
cp .env.example .env
# Edit .env — set your Git identity and (optionally) LLM API keys.

# Your GitHub token goes in a dedicated secret file, NOT in .env.
# The .secrets/ dir doesn't exist on a fresh clone, so create it first.
mkdir -p .secrets
echo "github_pat_yourtoken" > .secrets/github_token.txt
```

**2. Build** — compiles the image and strips privilege-escalation binaries.

```bash
make build
```

**3. Run** — starts pi in interactive TUI mode.

```bash
make run
```

> **Always use `make`, never bare `docker compose`.** The Makefile sets `WORKSPACE_DIR`, `HOST_UID`, and `HOST_GID` that every compose target depends on. A direct `docker compose run` skips that and gets them wrong.

## Configuration (`.env`)

Everything is driven by `.env`. Copy it from `.env.example` and fill in what you need — empty values are fine and simply disable that feature.

| Setting | What it's for |
|---|---|
| `HOST_UID` / `HOST_GID` | Your host user/group (`id -u` / `id -g`) so files the agent writes are owned by you. |
| `PARANOID_MODE` | `true` (default) blocks dangerous `gh` subcommands — see [Security](#1-paranoid-mode-gh-guard). |
| `GIT_NAME` / `GIT_EMAIL` | Commit identity inside the container. |
| `GIT_GPG_KEY` / `GIT_GPG_SIGN` | Optional commit signing. |
| `ANTHROPIC_API_KEY` / `OPENAI_API_KEY` / `OPENROUTER_API_KEY` | LLM keys — held by the proxy, never seen by the agent. Leave empty to skip. |
| `MEM_LIMIT` / `CPUS` | Container resource caps (default `4g` / `4.0`). |
| `SEARXNG_SECRET_KEY` | Session key for the local search sidecar — auto-generated by `make setup` if missing. |

### LLM API keys

Three providers are sandboxed through the **credential-proxy** sidecar: **Anthropic**, **OpenAI**, and **OpenRouter**.

```bash
ANTHROPIC_API_KEY=sk-ant-...     # https://console.anthropic.com/keys
OPENAI_API_KEY=sk-...            # https://platform.openai.com/api-keys
OPENROUTER_API_KEY=sk-or-...     # https://openrouter.ai/keys  (100+ models, one key)
```

Other providers (Gemini, DeepSeek, Mistral, Groq, xAI, …) are **not** proxied and won't be reachable from the agent, even if you add their keys.

**How the keys stay secret:** your real keys are injected into the **credential-proxy** container only — never into the agent. The agent gets the placeholder `proxy` instead, and on every start `pi-entrypoint.sh` writes `~/.pi/agent/models.json` so each provider's `baseUrl` points at the sidecar:

```
anthropic  → http://credential-proxy:8080/anthropic
openai     → http://credential-proxy:8080/openai/v1
openrouter → http://credential-proxy:8080/openrouter/api/v1
```

The proxy swaps `proxy` for the real key on the way out (`x-api-key` for Anthropic, `Bearer` for OpenAI/OpenRouter). The agent can call the models but the keys are never in its environment, its `auth.json`, or any file it can read.

> **OAuth / subscription users:** leave `ANTHROPIC_API_KEY` empty and run `/login anthropic` inside pi. OAuth tokens pass through the proxy untouched — it only injects a key when it sees the `proxy` placeholder — so Claude Pro/Max works unchanged. (Session is saved to `~/.pi/agent/auth.json`.)

Check what's active:

```bash
make providers
```

### GitHub token

The agent reaches GitHub two different ways, and they read the token from two different places:

| What you do | Path | Token source | Required? |
|---|---|---|---|
| `git clone` / `push` / `pull`, and the `gh` CLI | SUID **micro-vault** | `.secrets/github_token.txt` | Yes, for any git auth |
| GitHub **REST API** (`GITHUB_API_URL`, `gh api`) | **credential-proxy** | `GITHUB_TOKEN` in `.env` | Optional |

- **Git operations** always use `.secrets/github_token.txt`. This is the primary path and the one the Quick Start sets up. (Details in [Security §2](#2-the-micro-vault-github-token).)
- **REST API calls** are routed through the proxy sidecar. That route is only *authenticated* if you also set `GITHUB_TOKEN` in `.env` — in which case the token lives in the proxy container, never in the agent. Leave it empty and REST calls still work, just unauthenticated (subject to GitHub's anonymous rate limits).

> If you set `GITHUB_TOKEN` in `.env`, use the **same** token you put in `.secrets/github_token.txt`. Both files are gitignored.

A [**fine-grained PAT**](https://github.com/settings/personal-access-tokens) is recommended over a classic token.

## Everyday use

### Make targets

| Command | What it does |
|---|---|
| `make build` | Build the image. |
| `make run` | Start pi (interactive TUI). |
| `make run-args args="…"` | Run pi with specific flags/prompt (see below). |
| `make run-gpu` | Start pi with NVIDIA GPU passthrough ([details](#gpu-passthrough)). |
| `make run-with-db` | Start with a project network overlay ([details](#connecting-to-an-external-network)). |
| `make shell` | Open a shell in the container (runs as your host user). |
| `make shell-gpu` | Open a shell with GPU access. |
| `make providers` | Show which LLM providers are configured. |
| `make clean` | Stop and remove containers/networks. |
| `make update` | Rebuild the image from scratch (no cache). |

`make setup` (directory + secret-file scaffolding) runs automatically before `build`/`run`, so you rarely call it directly.

### Isolated instances

Each instance keeps its own pi/claude state, sessions, model selection and OAuth under
`.instances/<id>/`. A bare `make run` uses the persistent `default` instance; pass
`INSTANCE=<id>` to run isolated instances concurrently:

```bash
make run                    # persistent default instance (.instances/default/)
INSTANCE=review make run    # isolated instance (.instances/review/)
INSTANCE=feature make run   # a second concurrent instance — different model/session
```

Setting the model in one instance never affects another. The shared GitHub token
(`.secrets/github_token.txt`) is used by every instance. The workspace (`/workspace`)
is **not** isolated — instances share the same working copy unless you point each at a
different host path with `WORKSPACE_DIR=<path>`.

### Passing arguments

```bash
make args="--version" run-args               # check version
make args="/login" run-args                  # trigger a login flow
make args="'Create a snake game in python'" run-args   # one-off prompt
```

### Picking a model

- `Ctrl+L` — model picker across all active providers.
- `Ctrl+P` — cycle a scoped shortlist.

### Sub-agents on different models

Any of the three proxied providers can back a sub-agent. Just ask:

```
Run two reviewers in parallel: one using anthropic/claude-opus-4-5,
one using openai/gpt-4o.
```

> Pi runs every tool call without prompting — the equivalent of Claude Code's `--dangerously-skip-permissions`, on by default. If you want approval gating, install [`@gotgenes/pi-permission-system`](https://www.npmjs.com/package/@gotgenes/pi-permission-system).

## Claude Pro / Max as a provider

The image bakes in [`@gotgenes/pi-anthropic-auth`](https://github.com/gotgenes/pi-anthropic-auth), which reshapes pi's Anthropic requests so they pass Anthropic's first-party classifier. Combined with pi's `/login anthropic`, that lets you drive Claude on your Pro/Max subscription:

```bash
make run
/login anthropic     # open the printed URL on your host, paste the code back
/model               # pick a Claude model — the extension shapes the request
```

The OAuth session is written to `~/.pi/agent/auth.json` and persisted via the per-instance `.instances/<id>/.pi-data/` volume (default `.instances/default/.pi-data/`), so later runs of the same instance reuse the login. To confirm extensions loaded, check the `packages` array in `.instances/<id>/.pi-data/agent/settings.json`.

| `@juicesharp/rpiv-*` toolset | `rpiv-pi` (skills), `advisor`, `workflow`, `args`, `ask-user-question`, `btw`, `i18n`. |

## Bundled theme

Beyond pi's built-in `dark` and `light`, this image ships a custom **`darker`** TUI theme — a low-saturation dark palette with a teal accent and VS Code Dark+ syntax colors. Themes live in [`src/themes/`](src/themes/); `pi-entrypoint.sh` copies them into `~/.pi/agent/themes/` on every start and sets `darker` as the default **only when you haven't already picked a theme** (a manual `/settings` choice or an explicit `"theme"` in `settings.json` is never overwritten). Switch anytime via `/settings`.

## GPU passthrough

`docker-compose.gpu.yml` is an overlay that hands the agent your NVIDIA GPU(s) for local ML work (PyTorch, vLLM, etc.).

```bash
make run-gpu        # start pi with GPU access
make shell-gpu      # or open a GPU-enabled shell
```

Or point it at any project:

```bash
WORKSPACE_DIR=~/Repos/my-ml-project make run-gpu
```

**Requirements:** `nvidia-container-toolkit` on the host, with the `nvidia` runtime / CDI registered in `daemon.json`. The toolkit's OCI hook injects the host driver and `libcuda` into the (still read-only) container; CUDA-bundled wheels (e.g. `torch` cu12x) bring their own runtime, so nothing extra is needed in the image.

**What the overlay changes vs. the default:**

| | Default | GPU overlay |
|---|---|---|
| Memory | `4g` | `24g` |
| CPUs | `4.0` | `8.0` |
| PID limit | `150` | `4096` |
| GPU | none | all devices |

It also redirects Hugging Face / Triton / torch caches to `/workspace/.cache/…`, because the default cache locations sit on RAM-backed or `noexec` mounts that JIT-compiled kernels can't execute from.

## Working on a repo outside this folder

Point `WORKSPACE_DIR` at any host path; it mounts at `/workspace`, owned by your host UID so `git`/`gh` just work.

```bash
make run WORKSPACE_DIR=/home/me/Repos/my-project
# or export it once for the session:
export WORKSPACE_DIR=/home/me/Repos/my-project && make run
```

Defaults to `./workspace` if unset.

> ### First-run gotchas on an existing project
>
> The container has `python 3.11`, `uv`, `node 22`, `git`, `gh`, `gcc`, `build-essential`. Everything else must be installed **inside `/workspace`** — the only writable, executable place your tools can see.
>
> 1. **Stale virtualenv.** A host-built `.venv/` points at host-Python paths that don't exist in the container. Tell the agent: *"Delete `.venv/` and re-run `uv sync`."*
> 2. **Home-dir caches fail silently.** Everything outside `/workspace`, the named volumes, and a few tmpfs mounts is read-only. Code that writes to `~/.config/<app>/`, `~/.local/…`, `~/.<app>/` hits `EROFS`. Tell the agent: *"Relocate any `~/`-cache into `./.cache/` and gitignore it."*
> 3. **Built binaries in `/tmp` won't run.** `/tmp` is `tmpfs` + `noexec`. Builds must land in `/workspace` (or `node_modules`/`.venv`, which live there).
> 4. **No ports are published by default.** To expose port `3000`, add to `docker-compose.yml`:
>    ```yaml
>    ports:
>      - "3000:3000"
>    ```
> 5. **`localhost` is the container, not your host.** To reach a host service, add:
>    ```yaml
>    extra_hosts:
>      - "host.docker.internal:host-gateway"
>    ```
>    then use `http://host.docker.internal:<port>`.

**A good first prompt on a new project:**

```
This repo is mounted at /workspace. The container is read-only outside
/workspace. Before anything else:
  1. Delete .venv if present and run `uv sync` to rebuild against the
     container's Python 3.11.
  2. If the project caches anything under ~/ (e.g. ~/.<name>/), relocate
     it into ./.cache/ inside the workspace and gitignore it.
Then read README.md (or PRD.md) and continue from there.
```

## Connecting to an external network

Need the agent to reach a database or service in another compose project? Create a **gitignored** overlay:

```yaml
# docker-compose.db.yml  ← do not commit
services:
  pi-agent:
    networks:
      - myproject_db
networks:
  myproject_db:
    name: ${MYPROJECT_NETWORK:-myproject_default}
    external: true
```

Run it:

```bash
make run-with-db   # passes -f docker-compose.db.yml
```

Keep overlay files in `.gitignore`; a gitignored `Makefile.local` is a good home for project-specific targets.

## 🔒 Security Architecture

Defense-in-depth, in layers. Here's each one and — just as important — **what it does and doesn't cover**.

### 1. Paranoid mode (`gh-guard`)

A wrapper around the GitHub CLI. With `PARANOID_MODE=true` (default), these subcommands are refused:

> `gh auth` · `gh repo` · `gh secret` · `gh ssh-key` · `gh gpg-key` · `gh alias`

This stops the agent from re-authenticating, exfiltrating secrets, or planting a persistent key on your account. `alias` is blocked too, because otherwise `gh alias set x 'auth login'` followed by `gh x` would smuggle a blocked command past the guard. The guard also resolves the subcommand past any leading global flags, so it can't be dodged with `gh --flag auth …`.

### 2. The micro-vault (GitHub token)

Your GitHub token for **git operations** comes only from `.secrets/github_token.txt`:

- Mounted as a Docker **secret** (RAM-backed `tmpfs`), at a **randomized per-run path** (`/run/secrets/gh_<random>`), locked to permission `000`.
- The agent runs as an ordinary user (`UID 1000`), so reading the secret directly gets `Permission denied`.
- A small **setuid C binary** (`gh-vault`, installed as `/usr/local/bin/gh`) briefly elevates to root, reads the token into *its own* environment, drops back to your UID/GID, then hands off to `gh`. The token exists only inside that one short-lived process — never in the agent's shell or `process.env`.

*(The separate REST-API path via the credential-proxy is covered under [GitHub token](#github-token) above — that one reads `GITHUB_TOKEN` from `.env` into the proxy container, again never into the agent.)*

### 3. Two filesystem firewalls

Different layers with **deliberately different reach** — read this carefully:

- **OS syscall firewall (`LD_PRELOAD`, `fs-vault.so`).** Intercepts `open`/`fopen` for **every** process in the container, including native ones the agent might spawn (`cat`, `grep`, `python`). It guards the crown jewel — the pi **`auth.json`** (your LLM OAuth tokens) — and lets only the real `pi` binary through, matched by exact argv token (not a loose substring). This is the backstop against "spawn a shell tool to read the token."
- **V8 application firewall (`app-firewall.js`).** Monkeypatches Node's `fs` module and checks the call stack. When a read/write/copy/rename/symlink originates from the agent's tool directory, it throws `[SYSTEM BLOCK]`. It covers a **broader** set — `auth.json`, `credentials.json`, `.env` (but not `.env.example`/`.sample`/`.template`), `.secrets/`, and `/run/secrets/gh_` — for the agent's own file operations.

Between them: the pi auth token is protected against *any* process; the wider credential set (`.env`, `.secrets/`, …) is protected against the *agent's* operations and, on top of that, by plain filesystem permissions and by simply not being mounted into the container.

### 4. Privilege-escalation purge

At build time, escalation vectors are physically removed from the image:

> `su` · `mount` · `umount` · `passwd` · `chsh` · `chfn` · `chage` · `gpasswd` · `newgrp` · `login` · `nsenter` · `unshare` · `setpriv`

All remaining setuid/setgid bits are stripped (`chmod a-s`). The one intentional exception is the `gh-vault` binary above, which is added *after* the purge.

### 5. Safe persistence & no-exec scratch space

- **UID/GID mapping** — the Makefile passes your host IDs in, so files written to `./workspace` are owned by you, not root.
- **Read-only root** — the entire filesystem is read-only except `/workspace`, the named data volumes (`/home/node/.pi`, `/home/node/.claude`), and a handful of tmpfs mounts.
- **No-exec temp** — `/tmp`, `~/.npm`, `~/.config`, `~/.cache`, `~/.pi-lens` are `tmpfs` with `noexec`, so the agent can't download and run a static binary to sidestep the firewalls.
